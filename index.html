Image hosting benchmark

Does it matter where your images live?

Point this page at any image on any host — a bucket behind one of your own Cloudflare records, the bucket endpoint underneath it, the old site you are migrating away from — and it loads the same file from each one, one request at a time, timing every one in your browser with the Resource Timing API. It will also check that a file you have just moved arrived intact. Nothing is simulated and nothing is sent anywhere.

1. The places you are testing

Give each card a base URL — https://img.yourdomain.com/, a bucket endpoint, anything — and the image path from step 2 is appended to it. Or paste a whole image URL into a card and it is used exactly as it stands, which is how you compare one path on the old host against a different path on the new one. Mark one card as the original: the move check compares everything else against it.

A preset only fills in a name, a description and a placeholder — every card behaves the same way.

2. The image, and the test

Did the move work?

One request per host, read carefully rather than quickly: the bytes themselves compared against the card you marked as the original, plus the things that quietly break when images are copied from one service to another — the content type, the cache headers, the pixel dimensions, and whether a browser on your own site is even allowed to read the file.

How to read these numbers

A single run tells you very little. Networks are noisy, and the first request to a host pays for a DNS lookup, a TCP handshake and a TLS negotiation that later requests reuse. That is why this page runs several times, reshuffles the order each time, and reports the median rather than the average — one unlucky run cannot drag the median around the way it drags a mean.

Testing one of your own buckets

A card takes anything that answers over HTTP. For the img.yourdomain.com arrangement — a proxied CNAME to the bucket, a URL-rewrite rule that prepends the bucket name to the path, and a response-header rule adding Timing-Allow-Origin — paste https://img.yourdomain.com/ as the base and put the object's key in the image field. Paste the bucket's own endpoint into a second card and you are measuring exactly what the Cloudflare record in front of it is buying you.

One host on its own is a legitimate test. If you have just brought up a new img. record and only want to know how fast it is, tick one card and run it. The page reports the median, the spread, and whether that hostname permits cross-origin reads and sends Timing-Allow-Origin — which happens to be the quickest way to tell whether the response-header rule is really scoped to that hostname. What it will not do is invent a winner, because there is nobody to beat.

Moving an image from one service to another

Speed is the second question. The first is whether the file that arrived is the file you sent. Check the move fetches the image once from every host, compares the bytes against whichever card you marked as the original, and reports what is different. What it catches, in rough order of how often it actually happens:

  • The wrong content type. A copy made with a tool that did not set one lands as application/octet-stream or binary/octet-stream. The image still downloads, so a quick eyeball test passes — but browsers may save it instead of showing it, and CDN image optimisation will skip it.
  • A file that is not the same file. Something in the pipeline re-encoded or resized it. The byte comparison and the pixel dimensions both catch this; a digest of each copy is shown so you can record it.
  • Missing cache headers. An object uploaded without Cache-Control is re-fetched far more often than it should be, and the CDN in front of it cannot do its job. Images that never change are normally set to a year, and marked immutable.
  • Missing CORS or timing headers. If the new host refuses cross-origin reads, scripts on your own site cannot fetch the image, and this page cannot verify anything about it either. If it merely omits Timing-Allow-Origin, you lose the phase breakdown — for a Cloudflare-fronted bucket both are one response-header rule.
  • A path that does not exist. The most common one of all, and it shows up as a failed request rather than a slow one.

The move check requests every URL with a cache-busting token, so it describes what the host is holding now rather than what an edge cached before you replaced the file.

The two modes measure genuinely different things

Repeat visitor is the default, and the one that answers "where should my images live". Each request goes to a stable URL with only the browser cache bypassed, so a host with a CDN in front of it answers from its edge — which is what almost every real visitor gets, because someone near them has usually fetched the file already. This is the mode in which a CDN is allowed to show what it is for.

First visitor adds a unique ?cb= token to every URL. That misses the browser cache and the CDN edge alike, so each request travels all the way to the origin. It is the honest worst case, and it is the right mode for asking how quickly a host can produce a file it is not already holding near you — but reading it as the everyday number understates any host with a cache in front of it.

Repeat-visitor mode needs every host to permit a cross-origin read, because it is the only way to bypass the browser cache without changing the URL. If any one host refuses, the page says so and drops all hosts back to first-visitor mode — measuring two hosts by different methods would be worse than measuring them both pessimistically.

Whether the difference is real

A ratio on its own is not a result. If the run-to-run spread is wider than the gap being claimed, the ranking is noise dressed up as a finding. The page runs a Mann–Whitney U test on the two fastest hosts' samples — a rank test, because latencies are skewed and the samples are small — and says plainly whether the ordering survives. When it does not, the headline reads Too close to call rather than inventing a winner.

It also proves the hosts served the same file. Where a cross-origin read is permitted, the byte count is taken from the response body itself rather than from a header, so a host quietly serving a smaller or re-encoded image is caught and the comparison is flagged as not like-for-like. When that fires, the move check will tell you exactly how the two files differ.

Some hosts are not the same kind of thing

  • raw.githubusercontent.com is a convenience endpoint for reading files out of a repository. It is rate limited, it is not a CDN contract, and GitHub's terms do not cover using it as a production asset host. It is a great "does this work" URL and a poor place to point a live site.
  • GitHub Pages (username.github.io) is a real static host with a CDN in front of it. If you want the GitHub side of a comparison to be a fair fight, this is the URL to use, not the raw one.
  • Backblaze B2 is object storage. Hitting the bucket endpoint directly (f00x.backblazeb2.com, or the S3-style address) means going to one region every time, from anywhere in the world. Putting Cloudflare in front of it — the img.yourdomain.com arrangement — adds a cache at the edge and, through the Bandwidth Alliance, makes egress free. That is where B2 starts to look good on both speed and the bill.

So the interesting comparison is usually not "this provider or that one" but "is there a CDN in front of it, and how far is the origin from the visitor". The three cards the page ships with are exactly that experiment — raw GitHub, direct B2, and the same B2 bucket behind Cloudflare — and the shape of the answer usually appears in the first eight runs. Replace them all with your own the moment you have something real to test.

Things this page cannot see

  • Cross-origin hosts only expose a phase-by-phase breakdown (DNS, connect, TLS, waiting, downloading) — and the protocol they answered over — if they send a Timing-Allow-Origin header. Where a host does not, the table falls back to the total, and says so.
  • The move check reads the content type, size, cache and last-modified headers on any host that permits a cross-origin read, because those few are readable by default. Anything else, such as cf-cache-status or etag, needs the host to name it in an Access-Control-Expose-Headers response header, and reads as missing otherwise.
  • Nothing here can list what is in a bucket. Public object storage will serve you an object you name but will not enumerate its contents to an anonymous browser, so you have to supply the path. The page remembers the ones you have used.
  • Your result is your result: your city, your ISP, your Wi-Fi, this minute. It is evidence about your visitors only to the extent that they sit where you sit.
